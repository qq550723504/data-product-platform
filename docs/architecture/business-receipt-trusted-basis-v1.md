## 3. 来源接纳与 Receipt 使用的职责

| 责任方 | 拥有的判定 | 不可越过的边界 |
|---|---|---|
| IAM / 人员来源 Adapter | 认证、人员映射、当前资格及外部检查点 | 不由 IdP 角色、邮箱域名直接生成业务代表关系 |
| 业务责任与标准 owner | 代表/责任、适用与职责分离；确认标准权威来源 | 不把标准适用确认替代本单草稿确认 |
| Evidence / 来源接纳 owner | 原出处与内容身份、受控接纳规则、当前有效性、安全引用 | 原始 URI/metadata 不直接出 API；不将任意 Evidence 宣告可信 |
| Acceptance owner | 本单固定目标、当前角色、允许结果、证据资格及追加补正 | 不下载附件、不代签、不执行交付、不自造来源证明 |

未来来源核验通过 Port / Adapter 接入，Domain 不依赖具体 IdP、档案系统或对象存储 SDK。内部核验以服务器解析的 workspace、delivery、DatasetVersion、receiver party 和精确 evidence IDs 为输入；返回明确的可用/阻断/未知结论及强类型依据引用、内容身份、接纳规则版本、时点和有效期。浏览器不得提供 actor、receiver、来源信任、核验时间或接纳结论。

接纳引用必须能定位一条可审计、不可覆盖的决定及其内容/目标成员，不能只是任意外部 URL 或 metadata 中的 ID。现有 Evidence/evidence_relation 是记录与关联基础，不是已实现的可信接纳模型。具体来源选定后，Evidence owner 须定稿所需强类型事实与查询契约；无法提供这些依据时，Receipt 拒绝新 RECEIVED。本文不预先创建新通用来源服务、业务表或不明来源的 Adapter。

当前只读 v1 保持安全引用与 UNATTESTED/BLOCKED，不直接添加“可信”字段或放宽 Web 严格 DTO。未来若要展示接纳事实，须另行审核明确的版本化读取契约和权限范围。

### 3.1 接纳条件与最小事实

本节收敛T07–T10、T12中**用于RECEIVED的收到依据**，两条来源路径遵守相同条件；不是所有Evidence的统一准入。背景/争议引用及PARTIAL/MISSING/DISPUTED仍按第一切片的自身权限、范围和用途核对，可无附件。缺少来源记录不形成任何人的MISSING声明，接纳也不要求先存在Case、草稿确认或签收。

| 必须能够固定和核对的内容 | 最小语义与拒绝边界 |
|---|---|
| 明确来源及批准规则 | 已选择的受控来源/程序、记录和精确版本、可用材料类别、接纳规则版本及其适用依据；规则未批准、类别未知或仅外部verified标志均不可接纳 |
| 原始声明与资格 | 收到原文、所指内容、声明者和原声明时点的可信依据；分别保留录入者、发布者/服务账号及其出处，不把技术记录人当接收代表。原时点不明不得用本次核验时间补齐 |
| 原件及完整成员 | 数据与声明分别固定原件/内容版本、媒体类型、字节与编码说明、内容摘要及核对方法；冻结元信息与原件的可信关联依据，不能靠原文hash证明其外的时间/身份。全部必需成员及目标完整，不从分页截断或latest拼接 |
| 目标及用途 | 同workspace的明确delivery、实际DatasetVersion成员、接收party与effective consumer的对应依据，以及本次允许的材料用途；不能把一笔接纳扩张到其他交付、版本、主体或用途 |
| 核验责任与过程 | 核验责任主体、资格依据、规则版本、方法、实际核验时点及来源检查点；人按可信actor/canonical subject识别，自动核验按获准服务身份及责任方追溯，均不保存token。原声明时间、来源录入时间和本次核验时间分别记录 |
| 不可覆盖的接纳决定 | 稳定Core决定引用、对应Evidence/原件/目标的强类型关系、明确允许的用途、理由与核验依据；不是文件URL、来源ID或metadata布尔值。阻断/未知保留缺项与原因，不伪造可用决定 |
| 当前有效性依据 | 明确有效期语义、外部检查点/允许窗口及期限、当前处置的精确引用和判定时点；缺值不解释为永久有效，无处置记录也不替代完整性和时效核对 |

表中是未来业务事实的语义下限，不规定表名、字段JSON、hash协议或第五个Case Command。外部记录的决定可作为来源依据，不能直接替代Core的接纳事实；正式来源/受控程序仍须覆盖每一项条件。全部满足只说明材料可用于指定用途，不能自动生成BusinessReceipt、准备齐全、验收通过或交付权利。

### 3.2 接纳责任与形成规则

- 接收业务及来源owner负责选定材料类别、规则和有权办理接纳/处置的人员或服务，IAM负责可信身份与资格，Evidence owner拥有原件、核验与Core接纳事实；不存在“系统管理员默认可接纳/撤销”的权限。具体主体、授权范围与审核均待定，规则设计不授予权限。
- A的原声明者、录入者、发布者与读取/核验服务分别留据，原生记录或HTTP成功不代替有权代表的收到声明。B沿用来源评审稿的候选独立复核：复核与原提交者、经办人分别在actor及canonical subject上分离；该控制仍待G1明确批准，不在本节升级为已批准程序，也不增加Case角色或每次签收的复核步骤。
- 原声明资格在可信原时点核对；新接纳、复核及处置按各自动作的当前资格核对；接纳当前有效性另验。声明者后来离职/替任不直接改写原声明或撤销旧接纳，应按明确规则和当前依赖判断。有权Case RECEIVER可自行登记本单签收，但来源核验人、技术账号不能代签。
- 将来接纳与处置属于各自受权的Core写入，须有稳定幂等身份、明确目标与完整成员、审计/证据和领域事件；需异步副作用时同事务写既有Outbox。同次重放不重复事实，新的实际核验活动保留独立活动身份并按既有Cost规则留证；来源核验/接纳自身审计不反向成为原始收到证明。当前不实施或派发这些动作。
- 接纳决定及其内容/目标成员应在同事务完整形成并冻结，不允许late member追加改变历史；若将来引入暂存/Finalize，成员变更与冻结须共享parent lock/fence并在锁内校验完整成员与hash。具体模型和参与路径仍须G3/G4证明，本稿不声称已有DB约束。

## 4. 当前有效性与历史

1. **外部检查点**：来源网络检查在持业务锁前完成。必须明确来源版本、检查时点、有限有效期、撤销方式及允许窗口；断网、版本不明或超出允许窗口不产生新的可用结论。外部系统与 PG 无分布式原子提交，不能声称远端撤销必先于本地 commit 生效。窗口尚未选定/接受，保持关闭。
2. **本地最终判断**：Receipt 在同一业务事务内重新读取接纳、角色和目标依赖。影响本签收准入的本地接纳/处置路径须与业务最终判断共享串行化边界，复用既有事务与 workspace 依赖 fence 的组合 Port；不复制锁 key、不加独立锁服务。具体参与路径未证明完整时不得开启写入；通用 Evidence 读取/写入不因此全部获得新职责。
3. **不可变办理依据**：签收冻结当时具体材料、内容及接纳身份。后续原件变化必须成为新内容版本和新接纳引用；接纳撤销不能改原签收，只有当前准备情况仍依赖该接纳时才增加相应 blocker。需要更新收到声明时由接收代表追加补正，不自动改旧 outcome。
4. **有界读取**：仍按精确空间/父子关系、固定页码和有限材料数核对；不解引用浏览器 URL、不全量抓取企业目录、不输出下载凭据。原件读取、保留与删除策略须由实际来源决定后纳入启用清单，不在本轮新增上传或自动验真。

当前依赖从 Case 的显式当前指针选择，不能按 createdAt 或历史并集推断。例如符号引用 `r1(e1) → r2(e2)`：补正成功后 r2 为当前签收；e1 的接纳随后失效，且 r2 不再依赖 e1，则仅保留 r1 的历史/来源变化解释，不给 r2 新增 e1 的阻断项。若当前 r2 仍引用已失效的 e1，则按其冻结用途阻断；不能静默丢弃该成员、改用其他材料或改旧 hash。所有其他当前条件仍须独立满足；不因此放行引用 r1 的旧 submission，后续审核继续要求当前 receiptId 等于其冻结 receiptId。

只读恢复旧成功回执不重新计算“当时是否应成功”。材料的外部预查在持锁前进行，其错误只能影响无已提交回执的新写分支；不能抢先用来源断网、材料撤销或当前签收变化拒绝一个本人当前可读的 COMMITTED 回执。身份/空间 READ 仍须当前有效，不提供离线鉴权兜底。

### 4.1 失效影响与追加处置

未来处置必须指向明确接纳决定及受影响用途/范围，保留处置人及当前权限依据、原因、记录时间和明确生效时间；旧接纳、原件和签收成员不改写或软删除。当前投影由明确引用及已生效处置计算，不按最后时间猜当前、不因replacement存在就自动替换签收引用。以下是语义规则，不注册新状态枚举或HTTP动作。

| 变化或观察 | 必须采取的处理 | 保留的边界 |
|---|---|---|
| 原件/声明内容、来源版本、目标或允许用途需要更正 | 内容变化形成新内容版本；重新核验，满足条件后才产生新的接纳决定，明确关联被替代事实及旧决定退出当前用途的处置 | 内容未变、仅核验判断错误时保留原内容身份，追加失效处置和新的核验结论；再次接纳仍须独立满足条件，不为修正核验而新建DatasetVersion |
| 撤销、核验错误或明确替代已生效 | 指定旧决定在该范围不可供新使用；替代决定独立满足第3.1节，不能继承旧“可信”结论 | 替代不是补正签收，不自动移动Case当前签收指针；同一决定不得原地翻转结果 |
| 接纳有效期未到/已到期，或未来处置尚未生效 | 按锁内最终判定的新数据库时点检查，未到有效起点、恰到期/处置生效即不可新用；未来处置和有限检查点期限不能忽略 | 处置可提前记录，但不提前伪造已失效或覆盖当时事实；窗口外不得复用旧检查成功 |
| 断网、检查点过期、来源版本/处置不完整 | 当前可用性未知，不产生新RECEIVED可用结论；实际依赖它的当前准备情况受阻 | 不捏造永久撤销事实，不切换来源、自动补材料或重发；负面签收结果仍按自身依赖 |
| 仍被当前签收引用的依据失效 | 新写最终准入拒绝不满足条件的引用；既有当前签收的准备情况增加具体blocker | 原签收outcome/成员、旧提交/决定/档案不改；需新声明时由有权接收代表显式追加补正 |
| 已退出当前签收的旧材料单独失效 | 保留旧材料变化及其历史解释，当前判定只遍历显式当前依赖 | 不污染不再依赖它的新签收；旧submission仍按其冻结receipt匹配规则处理 |

本地新接纳、处置及任何会改变本次材料可用性的运行期路径，必须参加第一切片既有共享依赖fence和固定锁序；先持fence再重读。处置先提交则等待的新写拒绝；签收先提交则保留当时事实，后处置影响当前依赖。不得反向取得case锁或在另一连接做一次预检替代最终判断。完整路径未证明、远端允许窗口未确定或未获写授权时继续关闭。外部检查不在持锁期间进行，也不宣称跨系统原子撤销。

本节不改变原键恢复：当前本人仍有READ的已提交结果可只读恢复原事实；没有成功回执的新写才消费当前核验结果。NOT_OBSERVED不是未提交证明，关闭入口仍零POST。具体错误、回执/幂等分支与固定锁序仍以第一切片契约为准。

## 5. RECEIVED 的材料门禁

当前所有业务写入口均关闭，下列仅为未来登记准入：

- 至少一条真正符合受控收件材料类别、T07–T10 完整且当前可用的材料；所有提交的 evidence IDs 均须有权限、属于明确成果且满足其声明用途，不静默丢弃无效引用。
- 本人具备当前 RECEIPT_RECORD 与 READ、本单冻结 RECEIVER 仍有效、party 与交付接收主体相等；理由非空。具体字段与限制沿用第一切片契约。
- 缺来源/内容/接收主体或当前接纳依据时，以既有 `422 REQUIRED_CONDITIONS_NOT_MET` 和 `RECEIPT_EVIDENCE_UNAVAILABLE` 阻断，不借标准匹配或技术治理报告补齐。
- PARTIAL/MISSING/DISPUTED 可无材料但须非空原因，并满足其自身身份/责任/目标条件；它们全部阻断准备齐全。标准失效不应抹掉收到声明或额外阻止合规登记这些结果；当前全局关闭仍阻止全部新写。
