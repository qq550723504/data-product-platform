## 1. 当前结论与来源决策表

独立 1A 已实现逐用户 OIDC/RP、canonical principal/workspace 和本地事务责任 fence；1B 前置已能查询 Core 责任、标准及材料安全引用。企业人员、代表责任、标准权威依据、收件材料的实际来源均未选定。`CORE_RECORD_ONLY` 只是当前标准记录的来源标记；材料继续 `businessUse=BLOCKED`、内容与收件主体 `UNATTESTED`。既有测试证明协议与隔离，不证明现场真实来源。

| 依据域 | 当前可用事实 | 真实来源 / 业务确认人 | 选择来源后必须明确 |
|---|---|---|---|
| 人员身份与空间资格 | 独立测试 IdP、Core actor/binding/grant | UNCONFIGURED / 待指定 IAM 与业务负责人 | 稳定外部身份映射、人员有效性、空间授权、撤销和失效策略 |
| 代表关系与六类责任 | Core representation/responsibility 及追加处置 | UNCONFIGURED / 待指定接收组织责任方 | 谁可代表哪一 party、目标范围、有效期、分工依据及替任规则 |
| 标准与适用依据 | 明确 ContractVersion、完整标准集与适用关系 | UNCONFIGURED / 待指定标准责任方 | 来源版本的权威发布者、适用范围、原件可核验方式、确认权限 |
| 收件材料与收到声明 | 同空间且双关联的 Evidence 安全引用 | UNCONFIGURED / 待指定材料与接收业务责任方 | 受控材料类别、原记录者、内容身份、接收方声明、撤销及保留规则 |

来源选择不预设产品。可评估既有交付/工单/档案系统的原生只读接口；若没有可用系统，再单独设计受控人工接纳。普通上传、页面勾选、管理员手填“已验证”均不自动成为可信来源。系统、责任人和接纳方式未确定时，本表保持 UNCONFIGURED，不创建一个空壳来源注册中心或“临时信任”开关。

## 2. 最小可信依据清单

下列是未来服务端必须能核对、按明确身份引用的业务内容，不是当前 API 新增字段或客户端可提交的信任声明。

| 编号 | 必需内容 | 核对及保存要求 | 缺失时的含义 |
|---|---|---|---|
| T01 | 本人身份 | 已验证的 issuer/sub 映射到 canonical actor/subject；当前 READ/动作能力、workspace grant、revision 与期限 | 登录或当前资格不可用，不能办理 |
| T02 | 人员与组织关系 | 六类责任关联人员及空间资格可由权威来源确认；不收集其他参与人的 token | 合成身份、邮箱或显示名不能替代目录核对 |
| T03 | 代表与本单责任 | 明确 representation/responsibility IDs、party、目标、有效期、处置；复用完整绑定判定与职责分离 | 资产 owner、同组织、较新的绑定均不自动授予办理资格 |
| T04 | 明确交付成果 | 同空间的 ISSUED DeliveryOperation、其实际 DatasetVersion membership 和 effective consumer | BLOCKED/DEMO、名称匹配及 latest 不可建单；ISSUED 仍不证明收到 |
| T05 | 标准权威来源 | 明确 PUBLISHED ContractVersion、来源原件身份/记录摘要、完整 criteriaSetHash 与格式 | 不能用自由文本、AI 推断或缺省标准替代 |
| T06 | 标准适用与本单确认 | 明确适用 binding 与原确认责任；另有绑定精确 DraftRevision/hash 的本单确认 | “适用于成果”不等于“确认了这版草稿” |
| T07 | 材料出处 | 受控接纳方式、原来源记录/版本、可验证的原记录者、业务收到声明及其时间依据 | Evidence 类型、metadata 或 sourceType 字符串不是出处证明 |
| T08 | 材料内容身份 | 被接纳的不可变内容版本、内容 SHA256 的取得/验证方式；能追溯到当时内容及受控读取路径 | 平台记录 hash、URI、文件名或外部自填 hash 不替代原件内容核验 |
| T09 | 材料业务范围 | 同 workspace、明确 delivery/version；声明的接收主体与本单 effective consumer 匹配 | 单边关联、跨交付/版本/空间或接收主体不明均不可用 |
| T10 | 接纳决定及当前有效性 | 谁按哪版接纳规则确认哪些内容；接纳/处置的稳定引用、有效期、当前撤销结论及核对时点 | 只保存一个 verified 布尔值不足；UNKNOWN 不放行 |
| T11 | 签收办理依据 | 命令执行时的可信人员、代表/责任、材料及接纳引用、结果和原因；由服务器固定关联 | Command 自己的审计 Evidence 不反过来充当收到依据 |
| T12 | 历史可追溯性 | 原内容/接纳/签收记录保留；新内容、新接纳或补正有新身份并关联旧事实 | 不覆盖原记录、不按最新时间猜当前事实、不用软删除纠错 |

签收记录的是有权接收代表对明确成果作出的收到声明及其依据，不是平台自动裁定现实收货、法律权利或传输全部字节。内容 hash 证明可比较的内容身份，也不单独证明记录者、内容真实性或收到情况。

## 3. 来源接纳与 Receipt 使用的职责

| 责任方 | 拥有的判定 | 不可越过的边界 |
|---|---|---|
| IAM / 人员来源 Adapter | 认证、人员映射、当前资格及外部检查点 | 不由 IdP 角色、邮箱域名直接生成业务代表关系 |
| 业务责任与标准 owner | 代表/责任、适用与职责分离；确认标准权威来源 | 不把标准适用确认替代本单草稿确认 |
| Evidence / 来源接纳 owner | 原出处与内容身份、受控接纳规则、当前有效性、安全引用 | 原始 URI/metadata 不直接出 API；不将任意 Evidence 宣告可信 |
| Acceptance owner | 本单固定目标、当前角色、允许结果、证据资格及追加补正 | 不下载附件、不代签、不执行交付、不自造来源证明 |

未来来源核验通过 Port / Adapter 接入，Domain 不依赖具体 IdP、档案系统或对象存储 SDK。内部核验以服务器解析的 workspace、delivery、DatasetVersion、receiver party 和精确 evidence IDs 为输入；返回明确的可用/阻断/未知结论及强类型依据引用、内容身份、接纳规则版本、时点和有效期。浏览器不得提供 actor、receiver、来源信任、核验时间或接纳结论。

接纳引用必须能定位一条可审计、不可覆盖的决定及其内容/目标成员，不能只是任意外部 URL 或 metadata 中的 ID。现有 Evidence/evidence_relation 是记录与关联基础，不是已实现的可信接纳模型。具体来源选定后，Evidence owner 须定稿所需强类型事实与查询契约；无法提供这些依据时，Receipt 拒绝新 RECEIVED。本文不预先创建新通用来源服务、业务表或不明来源的 Adapter。

当前只读 v1 保持安全引用与 UNATTESTED/BLOCKED，不直接添加“可信”字段或放宽 Web 严格 DTO。未来若要展示接纳事实，须另行审核明确的版本化读取契约和权限范围。

## 4. 当前有效性与历史

1. **外部检查点**：来源网络检查在持业务锁前完成。必须明确来源版本、检查时点、有限有效期、撤销方式及允许窗口；断网、版本不明或超出允许窗口不产生新的可用结论。外部系统与 PG 无分布式原子提交，不能声称远端撤销必先于本地 commit 生效。窗口尚未选定/接受，保持关闭。
2. **本地最终判断**：Receipt 在同一业务事务内重新读取接纳、角色和目标依赖。影响本签收准入的本地接纳/处置路径须与业务最终判断共享串行化边界，复用既有事务与 workspace 依赖 fence 的组合 Port；不复制锁 key、不加独立锁服务。具体参与路径未证明完整时不得开启写入；通用 Evidence 读取/写入不因此全部获得新职责。
3. **不可变办理依据**：签收冻结当时具体材料、内容及接纳身份。后续原件变化必须成为新内容版本和新接纳引用；接纳撤销只改变当前准备条件，保留原签收和当时依据。需要更新收到声明时由接收代表追加补正，不自动改旧 outcome。
4. **有界读取**：仍按精确空间/父子关系、固定页码和有限材料数核对；不解引用浏览器 URL、不全量抓取企业目录、不输出下载凭据。原件读取、保留与删除策略须由实际来源决定后纳入启用清单，不在本轮新增上传或自动验真。

## 5. RECEIVED 的材料门禁

当前所有业务写入口均关闭，下列仅为未来登记准入：

- 至少一条真正符合受控收件材料类别、T07–T10 完整且当前可用的材料；所有提交的 evidence IDs 均须有权限、属于明确成果且满足其声明用途，不静默丢弃无效引用。
- 本人具备当前 RECEIPT_RECORD 与 READ、本单冻结 RECEIVER 仍有效、party 与交付接收主体相等；理由非空。具体字段与限制沿用第一切片契约。
- 缺来源/内容/接收主体或当前接纳依据时，以既有 `422 REQUIRED_CONDITIONS_NOT_MET` 和 `RECEIPT_EVIDENCE_UNAVAILABLE` 阻断，不借标准匹配或技术治理报告补齐。
- PARTIAL/MISSING/DISPUTED 可无材料但须非空原因，并满足其自身身份/责任/目标条件；它们全部阻断准备齐全。标准失效不应抹掉收到声明或额外阻止合规登记这些结果；当前全局关闭仍阻止全部新写。

## 6. 复用与待定项

继续复用现有 OIDC/RP、完整责任判定、ContractVersion、Evidence/hash、安全投影、transaction/Audit/Outbox。成熟身份和存储能力仍由已有 Adapter/OSS 承担，不引入第二套 IAM、RBAC、目录、上传或审批平台；平台拥有收到声明和准入的业务语义。普通文件上传和签章产品不能替代这套业务判定，具体产品选型待真实来源明确后再做必要评估。

当前待定：真实系统及责任人、原件取得/验证与保留方式、接纳事实的强类型模型、远端撤销窗口、正式人员映射、真实只读试点对象。以上均是未来写入前 blocker，不是待用户现在提供密码或手工操作的事项。入口和完成条件见[写入启用清单](../product/business-receipt-write-enablement-checklist-20261024.md)；本次不解决这些运行依赖。
