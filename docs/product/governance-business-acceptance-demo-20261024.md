# 新版业务签收、验收与归档演示

## 边界

本轮仅实现客户端交互，不实现后端 API、migration、权限、业务验收 aggregate 或 Command。沿用 DemoProvider 的当前工作空间/sessionStorage 隔离，新增 `business-acceptance-v1` 演示数据域，与既有 pipeline 演示及 Core 数据分开。DEMO-* 引用及演示角色均是合成状态，不构成服务端身份、签收、验收决定或归档事实。不调用模型、provider 或真实执行。

原库与 Agent API 保留。预览只刷新原记录的4188 UI进程；`refresh-web.ps1` 验证工作树、PID、启动时间和监听端口后操作，不停止 API、网关或数据库，不新增权限/夹具。本地 Core 只读证据入口仍为 `/core/archives`，展示名称改为“证据档案”；不与新增业务验收档案混为一谈。

## 新版入口

- `/#business-receipts`：业务签收；选择验收单、收到情况、签收依据与说明，追加签收记录并显式指向当前依据。
- `/#business-acceptances`：列表筛选、新建草稿、明确验收详情、编辑标准与来源、冻结提交、撤回、退回、重新提交、逐项通过、取消、决定作废。
- `/#business-archives`：独立归档列表、冻结提交/签收/标准/判断和原决定；支持回到对应验收，显示后续作废处置。

本地演示提供固定合成版本和授权已释放的交付样例；没有调用真正交付。不能从 Core BLOCKED 示例生成一条虚假签收。标准来源为明确标注的演示合约/需求/约定，可在草稿中编辑；不是后台标准版本查询。

## 交互约束

- 四种演示身份：提供方经办人、收件方代表、指定业务验收人、归档经办人；切换只用于演示，不改变登录身份。提交方与验收人分离。
- 未签收或部分收到、未收到、有异议时不可提交。完整签收需说明和演示依据。补正追加事实，不覆盖旧记录。
- 每次提交深拷贝标准和签收形成独立 submission；提交后签收依据变化时，不能直接验收通过，须退回/撤回并重新提交。
- 草稿只允许修改标准内容与来源；标准标识、必需性及核验方式保持原定义，不能通过保存草稿削弱必需条件。所有必需标准逐项通过且有说明，才允许通过。退回须明确至少一个未满足条目，或明确提交后的签收依据已变化，并写明原因。
- 重新提交保留原标准、签收、退回决定与核验结果。详情可展开各次冻结材料。
- 通过与归档是不同状态；归档只由归档经办人操作，重复归档复用原记录。
- 作废决定追加 disposition，原通过决定与档案仍保持原内容；档案显示当前决定已作废。首版作废后重新验收需另建验收单，不自动复活旧单。
- 模型校验预期 revision，拒绝过期操作；该校验只是本地演示，不声称提供跨客户端的服务端并发保证。
- 验收列表筛选、选中对象、办理身份和详情位置使用已有 session 演示存储，刷新可恢复；工作空间切换隔离。未增加第二套业务存储设施。
