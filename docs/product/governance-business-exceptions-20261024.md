# 业务签收、验收与归档异常流程验收

## 本轮范围

仅补齐本地演示的异常流程、追溯展示和浏览器回归。复用现有 DemoProvider、workspace/sessionStorage、历史记录与 UI；不新增后端 Command/API、migration、身份或工作流基础设施。不变更原库、权限或夹具，不接模型或真实执行；保留 Agent API。PR #363 保持 Draft，不合并。

## 发现的问题与修复

1. 签收依据变更会阻断通过，但页面没有明确显示 blockers，且退回强制要求某项业务标准 FAIL。修复为展示具体阻断原因；当冻结签收与当前签收不同，允许验收人说明原因后退回，保留逐项 PASS 判断，不伪造标准失败。仍不能直接通过，必须新提交冻结新签收。
2. 撤回事件没有引用明确 submission，重提后的旧提交无法准确显示撤回。新操作的事件追加明确 submission/receipt/decision/archive 引用，提交历史按其自身事实展示状态；不覆盖旧提交或猜测旧事件没有记录的关联。
3. 归档后作废只有笼统提示。现在分别显示原通过决定和后续作废处置的 ID、原因、办理人及时间；当前有效性与原决定分开展示。
4. 归档中的签收/提交只显示编号，不能明确回查。新增归档引用签收追溯标识，以及返回对应提交时自动展开该次冻结材料；缺少引用时明确提示，不能替换为最新对象。

冻结档案内容不因后续作废而重写；处置是单独附加展示。已取消、已通过的单据不能重新签收/提交；无有效通过决定不能新建归档。历史档案仍可只读查看。

## 自动化覆盖

`tests/browser/business-acceptance-exceptions.spec.mjs` 纳入既有 browser-contracts：

- 撤回必须由提交方填写原因；撤回、重提、再撤回、取消后刷新仍保留两次明确提交，取消后无法签收、提交或归档。
- 草稿取消必须有原因，不能生成提交、决定或档案。
- 提交后替换签收：即使标准全部 PASS 也不能通过；可因签收变化退回，原提交保留旧签收，新提交明确绑定新签收后才能通过。
- 已归档决定作废：原档案/提交/签收/通过决定保留，作废原因与人员可查，刷新保持；精确追溯档案签收及提交，重复查看不产生第二个档案。

每组用例结束都断言 fixture 业务 API 请求数为0。模型回归另验证签收变化退回不伪造 FAIL、撤回事件只引用其明确提交、取消后不产生决定或档案。不能将本地演示并发校验称为后端事务保证。

构建、Edge实走及新提交 CI 结果按实际执行分别记录；前一提交 ad818a33 的108项通过不延伸为本轮证明。
