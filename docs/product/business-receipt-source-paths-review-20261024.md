## 1. 评审要决定什么

先检查现有系统是否能通过原生只读能力提供必需依据；不足时评审受控人工接纳或明确的混合来源。人员、代表责任、标准和收件材料可以来自不同系统，但每条依赖都必须有明确责任方与可信路径。只读服务账号不获得代表人员签收的权限。

当前两条路径均未选择。所有真实系统、人员及业务批准人都**待指定**，来源保持 UNCONFIGURED；稿件、合成样例、技术 CI 或参与评审不构成选择、批准或运行授权。路径 A 不可用时不能自动切换 B，B 也不是无来源时的临时放行方式。

| 比较项 | A：现有系统只读接入 | B：受控人工接纳（候选） |
|---|---|---|
| 适用条件 | 已有交付/工单/档案等受控系统，能提供明确版本与收到声明 | 原始资料可核对，但现有系统接口或覆盖不足；业务方愿意建立有责任的接纳程序 |
| 人员与代表 | 企业认证及目录映射；来源原记录人、party/目标和权威依据可核对 | 同样需要可信人员及代表依据；不能靠手写姓名、上传者账号或管理员身份代替 |
| 收到依据 | 来源记录明确包含接收代表对该交付/版本的声明 | 接收代表的原始明确声明及内容引用，经受控采集与独立复核；不由复核人代作收到声明 |
| 内容身份 | 原系统不可变记录/内容版本及可复核原件摘要 | 固定当时原件及内容版本，核对字节、摘要和出处；文件名、截图或勾选本身不足 |
| 责任分离 | 分别核对声明者、录入者、发布者及各自依据；Adapter/技术账号只读取，不因记录来自原系统就成为有权接收代表 | 候选复核人与原材料提交者、经办人均须在actor及canonical subject上分离；不是新增Case角色或六类角色全部互异要求 |
| 撤销与时效 | 版本、处置、检查点/有效期和不可用行为明确 | 原材料、更正、复核决定及撤销均可追溯；当前有效性有明确负责方和核对规则 |
| G2 可做的事 | 另行授权后，只读核对源资料及其能否覆盖 T01–T10 的前置部分 | 另行授权后，对既有原资料作只读核对，不登记 Core 接纳或签收事实 |
| 未来 Core 留痕 | 来源读取是只读；保存接纳决定仍是独立受控写入 | 采集/复核结果正式持久化也属于写入，不能以“人工”绕过 G3–G8 |
| 当前判定 | 系统未确定，未连接，未见证 | 程序、具体责任人及接纳模型未批准，未实施 |

## 2. 责任与批准边界

下表定义职责，实际人员/账号均待指定。它不发放角色或权限，也不要求六个 Case 角色全部不同；沿用既有 PROVIDER 与 BASIS_CONFIRMER、PROVIDER 与 REVIEWER 在 actor 和 canonical subject 上的双重分离要求。

| 责任方 | 必须负责的内容 | 不得替代的业务动作 |
|---|---|---|
| 接收业务责任方 | 确认接收 party、谁可代表、哪些来源/材料类别可用；选择路径及接纳规则 | 评审通过不是实际收到或验收通过 |
| IAM / 人员责任方 | 稳定人员映射、当前空间资格与 READ；后续动作能力、期限/撤销边界 | 目录存在、邮箱或 IdP 角色不自动赋予代表关系 |
| 来源系统业务 owner / 接口 owner（A） | 原记录语义、记录人及版本可信性；只读接口、最小权限、完整分页和当前处置可查 | 技术下载完成、HTTP 200 或同步成功不自动等于收到声明 |
| 材料经办与独立复核职责（B） | 经办固定原件及出处；复核核对人员、内容、范围和接纳依据，并对核验结果负责 | 不能自审自批、修改原件后保留旧 hash、代替接收代表作收到声明 |
| Evidence / 来源接纳 owner | 安全引用、内容核对、版本/规则及当前有效性；未来强类型接纳事实与留痕方案 | 不能把普通 Evidence 类型或 metadata 标成可信后直接放行 |
| 标准责任方 / 本单 BASIS_CONFIRMER | 前者确认来源版本/适用依据；后者在建单后确认明确草稿 | 来源适用不能替代本单草稿确认，不能要求确认先于建单 |
| 本单 RECEIVER / Acceptance owner | 接收代表对本单登记或补正；Acceptance 按固定责任、目标、证据和当前权限办理 | 来源经办/服务账号不代签；签收不产生验收通过、下载或执行权利 |
| 运行与验收责任方 | G2 真实只读范围、G3–G5 实施/测试、G6–G8 运行申请与见证分别留证 | CI、文档或业务口头认可不自动开启写入口 |

B 的“经办/复核”是来源程序中的职责，不是第七、第八个 Case 角色或新的通用 RBAC 模块。候选控制为：复核人与原材料提交者、材料经办人**分别**满足 actor 不同且 canonical subject 不同；原提交者与经办人可以是同一人，不能由经办人再独立复核自己经办的材料。不同账号/角色名不能证明是不同人，可信映射无法证明分离时保持未知，不猜测邮箱或名称。具体人员、来源接纳资格及此候选控制的批准由 G1 定稿，当前未授予。

来源中的“作出收到声明者”“录入者”“发布者/服务账号”须分别有可核对的引用，不能因技术权限相同而合并成业务接收代表。原声明者按原声明的可信时点核对其当时代表依据；新的接纳经办/复核和Case办理按各自动作的当前资格核对，来源接纳当前有效性另行判断。原时点缺失时不以核对时间补齐，旧声明人的后来变化也不直接覆盖历史；后续处置与当前依赖仍按T10处理。

这些来源控制不要求每次 Case 签收再新增一个复核动作，也不禁止有权 RECEIVER 自己登记本单声明；Case 继续按原六类冻结责任办理，不让来源复核人代签。

## 3. A 路径：从既有权威记录只读核对

1. 由业务和来源 owner 明确受控记录类别及其含义，完成人员/party/目标映射，固定实际只读服务地址与权限；不接收浏览器任意 URL、token 或自填信任结论。
2. 当前人员在允许的空间/范围内选择**既有**明确 ISSUED 交付和实际成员版本。先由 Core scoped 查询核对目标；外部 ID 不替代 Core ID，也不建立对外部 ID 的数据库 FK。
3. 只读取已存在的原生记录或既有导出结果，核对精确版本、声明者/录入者、收到情况、原件身份和处置。来源 owner 须先明确端点的业务副作用；“GET”“查询”或“导出”名称不等于只读。新建导出/同步任务、确认已读/签收、生成新数据或交付凭据均不包含在 G2，只能列为待另行评审和授权的动作，不能为获得样本而触发。分页必须完整且属于指定版本，缺页/版本不明显示未知，不查 latest。
4. Evidence owner 通过受控读取能力核对内容摘要、声明中的接收方及交付/版本。原件核对不由 acceptance GET 去解引用任意 URI；不再次交付数据或签发下载能力来制造正例。
5. 另行授权的 G2 只记录核对能力、观察结果及缺口，不形成 Core 接纳或 RECEIVED。将来保存接纳事实、使用材料办理签收，需要来源模型/Port 定稿、实现和相应写入授权。

来源网络检查在业务锁外，检查点、允许窗口和有效期须事先接受；断网、来源版本不明或过期不产生新的可用结论。日后本地接纳/处置须参与既有事务最终重读和共享依赖 fence。远端与 PG 没有原子提交，不宣称远端撤销必能中止已进入的本地事务；不满足要求时继续关闭。

来源正常访问日志/安全审计可按其既有规则产生，它们不是业务接纳或签收事实。任何会改变业务状态、创建任务或释放新访问能力的副作用，都不能借只读接入隐含授权；当前真实端点及副作用清单未确定，不调用来源。

这里排除的是额外业务授权/交付能力，不否定已批准 IAM/RP 范围内的正常身份认证与会话处理。来源读取所需身份/凭据仅限明确授权的既有 READ 范围，仍遵循对应 IAM 契约；本稿不启动认证、扩大权限或新增凭据签发能力。

## 4. B 路径：受控人工接纳候选流程

```text
核对有权接收代表与目标 → 经办固定既有原件/声明和内容身份
→ 独立复核出处、代表、内容、范围及当前有效性
→ 按已批准规则形成可追溯接纳决定（未来写入）
→ 另由接收代表在已启用的 Case 流程登记/补正签收
```

当前只评审程序，不采集真实资料、不上传、不登记复核或接纳。未来只读见证可以检查已存在于受控渠道的原资料；新建平台材料、复核记录或接纳决定不是只读操作。

- 原声明必须由有权接收代表明确指向成果、接收主体和内容身份。经办记录其出处与提供方式，复核人核对声明者资格及原件一致性；不能把上传者、文件属性或文字里的姓名直接映射成可信 actor。
- 接纳决定应固定原件版本、摘要、目标/接收主体、核验人及依据、规则版本、时点和有效性，具备不可覆盖的追溯引用。真实来源选定后由 Evidence owner 定稿强类型模型及 Port；本轮不创建接纳表、通用审批平台或第五个 Case Command。
- 手工接纳不替代企业身份、代表关系或标准来源。普通邮件/截图可以是背景材料；缺少受控出处、可核对原件或接收主体时不满足 RECEIVED。电子签章、附件上传产品和自动验真不因本稿而进入首个切片。
- 更正内容须新原件版本与新接纳引用，旧决定/材料保留。撤销影响当前实际依赖，不自动改历史签收或将旧材料并入当前判定；原请求 UNKNOWN 的恢复继续按既有契约处理。

部分/未收到/争议必须是有权人的明确声明或其合法办理结果，不能从“来源查不到记录”推断；新增写入依旧须完整启用清单和另行授权。
