# Agent 质量闭环后端首期接入方案

状态：Q1 只读接口与页面已在本地隔离分支实现，通过接口、真实 PostgreSQL、前端构建、夹具浏览器验收及真实 Core 只读联调。Q2 及后续业务写入仍为设计提案；Q7 全流程执行验收仍待后续实施。日期：2026-10-23。验证边界见 [Q1 实施记录](agent-quality-q1-implementation.md)、[夹具浏览器验收](agent-quality-q1-browser-acceptance.md) 和 [真实 Core 只读联调](agent-quality-q1-live-readonly-acceptance.md)。

首期把现有 Agent 原型中的质量诊断流程接入真实平台：读取明确版本，确认诊断计划，执行质量检测，审阅修复范围，调用既有处理流程，独立复检，形成可追溯报告并人工审阅。继续采用确定性模板，暂不接模型。

正式界面逐步落到 `apps/web`，复用其 Next.js 服务端调用层；业务执行使用 `apps/platform` 的现有 Quality、Remediation、Workflow、Evidence、Audit、Cost、Outbox 和 worker。设计原型保留作交互参照，不把其 React 内存状态导入业务数据库。

## 首期范围

| 纳入首期 | 本期交付的业务结果 |
|---|---|
| Agent 工作台 | 当前受信工作空间内的真实委托列表、状态、阻断原因和历史查询 |
| 质量任务详情 | 诊断和修复分别确认；计划固定输入、规则和执行定义；执行与复检可回查 |
| 上下文侧栏 | 只引用所选任务的源版本、成果版本和明确评测；缺失时显示未知或缺少条件 |
| 既有质量闭环 | 检测、当前办理人认领、固定流程执行、失败后显式重试、独立复检 |
| Agent 报告 | 固定证据引用、人工接受或退回、关联新委托、服务端授权导出 |
| 恢复与隔离 | 刷新后恢复；同请求重放不重复产生业务工作；跨空间拒绝；未知不猜测为失败 |

本期不纳入需求管理与开发方案全生命周期、自由编排任意工具、通用规则编辑器、模型推理、Agent 自动发布与交付、任意成员分派、完整 IAM 或对整个白皮书的真实功能实现。认证、发布、交付页面可导航到既有业务入口，仍各自执行原门禁。

## 原型与后端的三个关键差异

### 修复依赖完整批次

原型的修复按钮把单个版本作为输入。现有后端的受控修复模板要求：同一已接纳 ingestion receipt 的三份 RAW，加上从指定来源产生的成功 STANDARDIZED 实体解析版本，再输出到模板指定的 CURATED Dataset。`LoadPlan`、`validateInputs` 和执行命令会验证这些关系。

首期保留这些业务条件。单个可用 RAW 可以进入诊断；缺少批次或解析成果时，修复页列出具体缺口并引导已有接入、实体审核页面。不得自动选择其他批次、最新解析成果或其他输出资产来凑齐输入。其他 Dataset 类型先提供已有评测的授权查看，不承诺本修复模板可执行。

### 分派目前是当前办理人认领

后端 `assign` 的 actor 来自受信 principal，后续处理要求 actor 等于当前认领人。请求体没有“任意空间成员”字段。首期按钮使用“由当前受信办理人认领”，不能把原型的演示办理人选择当作真实身份。多人协作在后续身份与成员映射设计中处理。

### 暂停和停止不等同于引擎取消

后端公开 Workflow 接口具有执行、查询和重试，不应从 domain 枚举推断已存在暂停或取消引擎的 API。首期暂停只阻止 Agent 受理下一动作；已受理动作继续按原业务记录核实。未决动作存在时禁止把委托直接标记为已停止，界面提供暂停后续动作与查看原运行。

## 能力对照

下表的“已有”只表示当前代码存在，不表示当前运行环境已经启用或本次完成 live 验收。

| 页面动作 | 当前能力与源文件 | 首期接入方式与缺口 |
|---|---|---|
| 选择 Dataset 与版本 | `readmodel/transport/http/handler.go`、`dataset/transport/http/handler.go` | 复用查询与 scoped repository；新增 Agent 上下文查询统一验证 principal、workspace 与对象归属 |
| 查看质量、明确历史报告 | `quality/transport/http/handler.go`、`apps/web/lib/quality-server.ts` | 复用精确 assessment/attempt 查询；保留局部 UNKNOWN，不回退为其他报告 |
| 发现支持的异常 | `quality/remediation/application/service.go` 的 `Detect` | 调用既有命令；Agent 记录检测请求关联；补按业务请求键查询 detection 的恢复能力 |
| 选择标准和修复模板 | `quality/remediation/application/plan.go`、industry pack YAML | 展示服务器已配置模板及其 hash；原型 STD 编号不是后端规则契约；不允许浏览器提交任意文件路径 |
| 认领与处理 | `quality/remediation/transport/http/handler.go` 的 `assign/execute` | 复用命令，固定真实 actor、输入集合、workflowVersion、输出 Dataset 和期间 |
| 重试 | 同模块 `retry`，以及 `workflow/application` | 区分原请求重放与新物理工作；已失败且明确允许重试才创建新的关联执行 |
| 核实未知结果 | 既有 Execution、Quality attempt、case detail 与业务 reconciliation | Agent 追加引用与观察；去掉“模拟核实已成功”选择，不让操作者填写实际运行结果 |
| 独立复检 | 既有 `recheck` 与质量报告 | 固定具体 executionLink 与实际输出；复检不通过不得冒充完成修复 |
| 结束业务处置 | 既有 `close` | 仅作手工关闭事实；不映射为质量通过、认证通过或 Agent 报告接受 |
| Agent 确认、修订、报告审阅 | 当前未发现完整对应的持久化模块与公开 API | 新增有限的 Agent 委托应用能力；引用现有业务事实，不建立第二套执行结果账本 |
| 需求转方案、新业务需求 | 产品模型中有 `use_case_id` 引用，但未发现原型整套需求/方案命令 | 转后续切片；本期关联重办只创建新 Agent 委托，不声称创建真实 UseCase |

## 页面和操作调整

保留工作台、任务详情、上下文侧栏三类已确认界面。数据模式从本地演示迁入真实模式后，字段必须来自后端查询，禁止接口失败后用合成记录填充。演示模式与真实模式使用明确入口和标签，业务状态不互相写入。

| 界面 | 首期真实模式行为 |
|---|---|
| 工作台 | 显示 QUALITY_DIAGNOSIS；需求转方案保留设计预览标签，不提供真实执行按钮 |
| 计划确认 | 展示源版本、配置模板版本/hash、诊断规则/hash；修复确认增加完整输入、输出与 workflow/hash |
| 执行与恢复 | “执行下一步”提交明确动作请求；页面展示业务 owner 的原始状态和最新已知观察 |
| 补充计划 | 服务器重新准备修订；检测开始后换源版本需新委托；规则变化重新确认 |
| 异常状态 | 已知失败、业务阻断、读取未知分别显示；未知保留原 request/action/attempt ID |
| 成果与审阅 | 证据充分才开放接受；退回必须说明并创建关联新委托；旧报告与旧版本继续可查 |
| 侧栏 | 来源与成果分别标注；没有任务对象时需要用户明确选择，不带入另一页面残留版本 |
| 业务交接 | 使用明确 dataset/version/case/execution/report 链接，不跳转到“当前最新”替代记录 |

## 实施清单

Q0 的设计基线已固定，Q1 已完成代码、本地测试、夹具浏览器验收及真实 Core 只读联调；其余业务工作包尚未实施。依赖顺序是 Q0 → Q1 → Q2 → Q3 → Q4 → Q5，Q6 随各包补充，Q7 最后执行。编号是本地计划编号，不代表已创建 Issue。

| 编号 | 优先级 | 交付内容 | 依赖与验收重点 |
|---|---|---|---|
| Q0 | P0 | 固定本契约、现有接口清单、写入范围、身份与业务模板 | 不扩建需求系统、IAM、通用 Agent runtime |
| Q1 | P0 | Agent 上下文授权查询，迁入 `apps/web` 的只读页面 | 同空间/跨空间/缺凭据；精确历史报告与局部 UNKNOWN |
| Q2 | P0 | 委托、原子冻结的计划修订、两阶段确认、动作意图、审计/证据/outbox | PostgreSQL 真实事务与并发验证；刷新可恢复；旧确认不能消费新修订 |
| Q3 | P0 | 既有 Detect 适配与按请求键查收据；无异常和不支持规则分支 | 同键同请求仅一次评测；响应丢失后仍能找到无 case 的诊断结果 |
| Q4 | P0 | 认领、执行、重试、复检适配；现有 worker/outbox 的有限动作处理器 | 完整四输入；固定输出；跨事务恢复；不重复实际工作与成本 |
| Q5 | P0 | Agent 报告冻结、审阅、关联重办与授权导出 | 原报告不覆盖；接受不改变 case/Quality/认证/发布/交付事实 |
| Q6 | P0 | 领域、应用、接口与 PostgreSQL 回归 | 逐项对应下列验收用例；修复根因而非前端绕过错误 |
| Q7 | P0 | 隔离环境 live-core 浏览器验收与证据清单 | 固定测试主体、数据、模板 hash；不介入现有保留运行环境 |
| Q8 | P1 后续 | 需求转方案的 UseCase/业务方案/WorkflowVersion 映射 | 单独业务切片；不以原型 JSON 直接补 CRUD |
| Q9 | P1 后续 | OIDC/成员角色映射、多办理人协作；受控模型建议 | 复用标准身份能力；模型不得直接授予权限或提交未批准动作 |

实施启动前核对当时的工作区、活动 writer 与相关 Issue/PR，领取单一写入范围。本方案不为其他正在处理的切片重复派工，也不改变已有环境、凭据或数据。

## 首期验收

| 用例 | 必须观察到的结果 |
|---|---|
| A01 只读与身份 | 未配置/错误凭据被拒绝；合法主体的其他空间对象不可读取；GET 不新增业务事实 |
| A02 计划与确认 | 未确认无实际工作；换输入、规则或 workflow 后旧确认失效；并发修订与动作受理得到确定顺序 |
| A03 支持的主线 | 同批三 RAW + 正确解析版本 → 检测 → 二次确认 → 认领/执行 → 新 CURATED → 精确复检 → 报告审阅 |
| A04 缺少依赖 | 缺 receipt、替换任一 RAW、错误解析父版本、错误输出 Dataset 均阻断修复；不新增修复调用成本，已发生的检测成本保留 |
| A05 无异常与其他规则 | 无 case 不等于全部通过；只在精确评测 PASS 且无支持异常时走无修复报告；其他结论显示实际阻断/警告 |
| A06 幂等与崩溃 | 双击、响应丢失、outbox 重复投递、业务已提交但 Agent 收据未写回，均恢复同一业务请求 |
| A07 失败与重试 | 超时保留未知；未决禁止新执行；已知失败后显式批准新工作，形成新 Execution/关联与实际新增成本 |
| A08 暂停与停止 | 暂停前后受理次序有 parent lock 保证；未决动作可继续核实，不能被停止状态掩盖 |
| A09 历史报告 | 后续评测出现、列表失败或 latest 失败时，明确选中的旧报告不会被替换；导出再次鉴权 |
| A10 审阅与重办 | 退回保留旧报告；新委托新确认；接受只结束委托；手工 case close 不能当作复检通过 |
| A11 证据与计量 | 每次实际工作由已有 owner 记账，Agent 查询/展示不重复计费；关键决定有同事务审计、证据与事件 |
| A12 有限试点边界 | UI 不含服务凭据，不信任演示 actor/任意 workspace，未开放发布/交付和模型工具执行 |

单元测试和 CI 通过、隔离 live-core 验收、保留环境上线、生产可用性分别记录；不能相互替代。现有原型 43 项测试覆盖的是合成演示，不能作为以上后端用例已通过的证据。

## 评审结论与下一阶段入口

建议先批准 Q0–Q1 的契约和只读接入，再按相同切片逐步实现持久化与真实命令。评审应确认：限定的受信办理人/工作空间、使用的已接纳批次、现有固定修复模板，以及原型三个差异的界面口径。具体环境与数据 ID 在独立验收计划中绑定，不在设计文档中假定可用。

本轮仅新增设计文档；没有新增迁移/API、启用操作开关、执行数据处理、连接模型、创建外部 Issue/PR 或修改保留运行环境。
