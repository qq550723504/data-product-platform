# ADR-0014：全生命周期治理扩展与既有生产事实边界

- 状态：提议；随对应文档 PR 合并后成为目标架构边界，不代表新增运行能力已实现。
- 日期：2026-10-10。
- 关联：#296 / #297；[产品蓝图 V2](../product/full-lifecycle-governance-v2.md)。
- 保持有效：ADR-0002/0003/0004/0010/0011/0012/0013 与 AGENTS；本 ADR 不撤销已有业务 invariant。

## 背景

现有平台以不可变 DatasetVersion 为中心，已验证 Certified/Gold 的受控生产与交付。产品负责人现在要求治理覆盖发现、准入、加工、使用、持续监督及生命周期终止。

仅把所有外部数据搬进 Core、复制一套 OpenMetadata、增加全局治理 status，或一次部署更多引擎，都不能解决跨系统责任与事实一致性问题。新范围需要边界，而不是新的万能平台模型。

## 决策一：区分外部资产纳管与版本化生产

外部数据库、表、文件和 API 可以先被发现、绑定、描述与观察，不要求先复制业务内容。它们仍是外部资产，不自动成为 DatasetVersion、Certified Dataset 或获准交付的数据。

Core 接纳有界且可验证的内容/manifest 后，才形成平台 DatasetVersion。外部持续变化的表、view 或 CDC stream 不能冒充不可变内容；版本 cut/window、源身份和内容验证继续遵循 ADR-0011。

只在首个实际切片中扩展现有 DataResource/ResourceBinding 等必要边界，不提前新建通用资产超级实体、全局 GovernanceJob 或多套版本模型。

## 决策二：按事实划分写入权，不按“一个系统拥有所有元数据”划分

| 事实 | 权威 / 写入 owner | 与另一侧的关系 |
|---|---|---|
| 源系统实际 schema、物理对象与访问能力 | 源系统；OpenMetadata/Adapter 观察并记录来源与时间 | Core 保存稳定绑定和必要接纳证据，不把旧观察当当前源状态 |
| 技术目录、术语、描述性分类和技术血缘 | 按 ADR-0002 由 OpenMetadata 承载或投影；每个字段只选一个作者侧 | 具体同步方向/冲突规则在 B 冻结；不建设双主编辑 |
| Core Owner/workspace、DatasetVersion、实际输入/输出血缘 | Core | 外部 Owner 显示或同名对象不能覆盖业务归属；经批准 Command 才更新可变归属 |
| 已用于生产/认证的规则、Contract、质量与权利事实 | Core 的明确版本/快照与既有领域模型 | 可引用外部草案/观察，但门禁使用已接纳事实，不能查询 current tag 作为唯一依据 |
| 运行中的技术作业与 checkpoint | 外部引擎 | Core 持有业务 Execution/attempt；成功状态只触发接纳，不直接认证 |
| Certification、ProductRelease、Delivery、Evidence/Cost/Audit | Core | 继续作为治理投影输出；外部删除/编辑不回滚历史业务事实 |

B 必须固定 workspace-owned connection、provider instance/object identity、字段 owner、同步方向、观察/源版本、冲突与失联行为。显示名称或路径可变，不能单独用于认定资产相同；具体字段由已有 binding 能力与实际需求决定。

门禁相关的新策略只有经明确版本化接纳和受控启用后才能影响当前动作。会影响当前拒绝/授权的变更，要由相应生命周期 Command 与 fence 机制落实；异步目录投影不是实时撤销通道，也不能用“已冻结旧快照”规避当前权利检查。无法确认所需当前授权时 fail closed。元数据引擎故障不改写既有 Release。

## 决策三：治理规则与执行动作协作，但不制造双调度

Core 定义本次要使用的输入、用途、规则和应记录的业务结果；成熟引擎承担连接、搬运和计算。继续复用 Worker/Outbox/Reconciliation，遵循 ADR-0010/0011。

接入先做单来源选型；Native/Hop 优先复用；dbt 与 DolphinScheduler 仅在其真实能力缺口出现时进入后续评估。dbt 引入前须明确 SQL 数据面和输出冻结边界；Core PostgreSQL 的存在不等于已具备业务数仓。

同一操作只允许一个调度/技术重试 owner。Core 的结果对账不应独立再次启动同一工作。外部调用采用已有 DB-first 请求/attempt、unknown outcome 与恢复规则；新实际调用独立记录成本，不以业务最终成功作为发生过调用的前提。

连接、预览、Profiler、加工和交付分别验证权限与范围。标签、Owner、目录可见、技术连接成功、同一登录账号均不能代替实际数据面授权。外部组件不能成为绕过平台受控交付的公开后门。

## 决策四：闭环修复不改写历史，也不自动授予认证

数据内容变化 → 新 DatasetVersion；仅评测纠错 → 新 QualityAssessment；认证变化 → 新 Certification/Disposition。复用既有严格语义，不增加另一套“已治理=可交付”的布尔状态。

外部 Profiler/告警是带来源、范围与观察时间的信号。只有确实绑定本次冻结数据和适用规则的评测，才可用于对应质量/认证决定；外部 live source 的通过结果不能直接复制给某个旧版本。

人工关闭工单不代表质量通过。规则修复不得以无依据补值掩盖源数据缺失；隔离样本和错误日志也属于需要权限、保留和处置管理的数据。

## 决策五：生命周期终止先设计，不能借文档绕过 immutable guards

区分三种关注点：历史版本/决策事实、当前使用资格、物理内容可用性。它们是设计维度，不是本 ADR 新增的数据库状态或 API。

本轮不允许改写、软删除既有历史，不新增数据删除能力。D-design / #300 必须先解决：

- 保留策略起算、保全与处置授权，以及与当前 gate/活动读取/恢复的并发边界；
- 数据集、派生/共享对象、标注/隔离 payload、索引/缓存、备份、外部副本的具体覆盖与责任；
- Provider 部分成功、响应丢失、unknown 与可验证销毁范围；
- 备份恢复不能绕过已生效的停止使用或删除约束；
- Evidence/Audit 本身含敏感内容时的保留、删减、密钥/内容引用及历史验证能力说明。

一般性不可变约束不是永久保存所有敏感内容的理由；hash 也不是匿名性保证。但解决这些问题必须先有专门契约和必要 migration，不能直接删除冻结正文或保留一条假的“仍完整可验证”记录。D-design 必须明确对现有契约的必要演进，再做有界实现。

业务批准、发出删除请求、主对象不可见、已验证某范围物理处置和外部副本已确认，是不同事实。缺少外部确认不得声称全域销毁。保留期限与法律保全由适用政策及责任主体确认，本平台不自动裁定法律要求。

## 决策六：增量范围与审查收敛

A / #297 只产文档；B / #298 只扩单来源切片；C / #299 只扩有限异常/变化闭环；D-design / #300 只设计终止契约。D-runtime 另行立项。新战略不修改 #294/#295，不重开已完成 Certified/Gold 的历史验收，不复制 #84/#86/#87。

沿用 AGENTS §17：冻结 goal、权威文件、in-scope invariants、非目标和 merge blockers。三轮 substantive review 或二十条已解决 comments 后做收敛检查，未来通用能力转 follow-up。技术可合并不等于获得部署或真实数据授权。

## Build-vs-Buy / Reuse Check

既有 Core 版本/权利/评测/认证/交付、MetadataEngine/ResourceBinding、Native/Hop、存储、Worker/Outbox 都保留。成熟目录、采集、SQL 转换、调度、身份和存储保留能力不从零复制；新引擎须记录具体 license/edition、维护与运行成本、API 和恢复/替换边界。

本 ADR 选择的是责任分配与增量准入，不是最终 SeaTunnel/dbt/DolphinScheduler 选型；没有新增运行时、依赖、schema、自动化删除或治理引擎。

## 后果与非目标

收益是纳管范围扩大而不稀释可验证生产事实；代价是需要明确元数据绑定/写入权、信号接纳、处置范围和陈旧/未知状态。

不在本 ADR 设计全量治理状态机、通用 Policy DSL、跨系统实时一致性平台或所有未来异常。既有专门领域文档保持权威；发生必须演进的冲突时，后续具体 Issue 应同步修改权威契约，而非在总览中暗改。
